# InstantDB Legacy Server — Reactive Sync Engine Spec

Source of truth: the Clojure server under `LEGACY/server/src/instant/`. This document
describes the wire protocol and internal machinery of the reactive sync engine precisely
enough to build a wire-compatible Rust reimplementation. All file references are relative
to `LEGACY/server/src/instant/` unless noted; client references are relative to
`LEGACY/client/packages/core/src/`.

Key files:

| File | Role |
|---|---|
| `reactive/session.clj` | WS/SSE session lifecycle, all op handlers, receive-queue worker |
| `reactive/receive_queue.clj` | thin wrapper over the grouped queue holding inbound events |
| `reactive/query.clj` | instaql-query execution layer + datalog cache/subscription bookkeeping |
| `reactive/store.clj` | in-memory datascript store: sessions, queries, subscriptions, caches, topic matching |
| `reactive/invalidator.clj` | WAL consumer: transforms WAL records, stales queries, enqueues `:refresh` |
| `reactive/topics.clj` | WAL change → topic conversion |
| `reactive/ephemeral.clj` | presence/rooms hub (Hazelcast-backed) |
| `grouped_queue.clj` | per-key serialized work queue with combining |
| `lib/ring/websocket.clj` | undertow WS adapter, ping/idle logic, `send-json!` |
| `util/exception.clj` | typed exceptions that become `:error` messages |

## 0. Wire format fundamentals

- Every message in both directions is a JSON object (or, for batched server sends only, a
  JSON **array** of objects — the client accepts `Array.isArray(e.message)` and iterates,
  `Reactor.js:1798`).
- The server serializes with cheshire (`util/json.clj:39` `->json` = `cheshire/generate-string`).
  **Keyword keys serialize as their name with kebab-case and any `?`/`@` preserved**:
  `:client-event-id` → `"client-event-id"`, `:unique?` → `"unique?"`,
  `:processed-tx-id` → `"processed-tx-id"`. Namespaced keywords keep their namespace
  (`:instant.grouped-queue/put-at` → `"instant.grouped-queue/put-at"` — such internal keys
  can leak into an error's `"original-event"` echo; harmless, the client ignores them).
  Keyword *values* serialize the same way: `:init-ok` → `"init-ok"`, `:one` → `"one"`.
  UUIDs → strings. `java.time.Instant`
  → ISO-8601 string (`util/json.clj:26`). The `ISN` type → string `"<slot-num-hex>/<LSN>"`
  e.g. `"0/1A2B3C4"` (`isn.clj:52,58`).
- Inbound messages are parsed with keywordized keys and `:op` coerced to a keyword
  (`session.clj:1245-1248`):

  ```clojure
  (defn on-message [{:keys [id receive-q data]}]
    (receive-queue/put! receive-q (-> (<-json data true)
                                      (update :op keyword)
                                      (assoc :session-id id))))
  ```
- Every server→client message gets `:trace-id` assoc'd in `rs/send-event!`
  (`store.clj:1599-1601`), so all payloads described below additionally carry a
  `"trace-id"` string field. The client surfaces it in error messages.
- Every client→server message carries `"client-event-id"` (a UUID generated by the client,
  `Reactor.js:1744`: `this._transport.send({ 'client-event-id': eventId, ...msg })`).
  Handlers echo it back in their `-ok` responses.
- Transport is WebSocket at `GET /runtime/session` (`runtime/routes.clj:50-53`,
  `session-get`), with permessage-deflate enabled (`lib/ring/websocket.clj:187-189`,
  deflate level 6). Session id is a datascript `squuid` generated server-side at connect.
  There is also an SSE fallback transport (`undertow-sse-config`, below).

## 1. Session lifecycle

### 1.1 WS connect (`session.clj:1240-1324`)

`undertow-config` builds the undertow websocket callbacks:

- `on-open` (`session.clj:1240-1243`): builds a `socket` map
  `{:id sess-id :http-req exchange :ws-conn channel :receive-q receive-q
  :pending-handlers (atom {}) :get-ping-latency-ms fn}` and stores it in the session store
  via `rs/assoc-session! store sess-id :session/socket socket`. **Nothing is sent to the
  client on open.** The session exists but is unauthenticated until `init`.
- `on-message` (`session.clj:1245`): parse JSON → put on the receive queue (see §8 for
  ordering).
- `on-error` (`session.clj:1262`): IOException ignored; others logged.
- `on-close`: see §1.4.

Ping/keepalive (`lib/ring/websocket.clj:113-151`): server sends a WS **ping frame** every
`ping-interval-ms` = **5000 ms**; if no frame of any kind (message/pong) has been received
for `idle-timeout-ms` = **15000 ms** the server closes the socket. Pong latency is recorded
(`onPong`) and exposed as `ws-ping-latency-ms` in tracing only. There is no
application-level ping op; the client relies on WS-level ping/pong.

### 1.2 `init` (`session.clj:154-196`)

Client sends (see `Reactor.js:1762-1773`):

```json
{ "op": "init",
  "client-event-id": "<uuid>",
  "app-id": "<uuid>",
  "refresh-token": "<token or absent>",
  "versions": { "@instantdb/core": "v0.22.x", "@instantdb/react": "..." },
  "__admin-token": "<uuid or absent>" }
```

Server-side steps, in order:

1. If session already has `:session/auth` → validation error
   ``"`init` has already run for this session."`` (`session.clj:157-159`).
2. `app-id` required, coerced to UUID (`ex/get-param!` → `param-missing`/`param-malformed`
   errors otherwise).
3. Load the app (`app-model/get-by-id!`, 404-style `record-not-found` typed error
   with hint `{"record-type": "app", "args": [...]}` if missing/deleted).
4. Load attrs for the app (`get-attrs`, `session.clj:144-152`; normal apps:
   `attr-model/get-by-app-id`; byop apps introspect their own pg schema).
5. If `refresh-token` present: `app-user-model/get-by-refresh-token!` → the user, else
   typed `record-not-found` error with hint `{"record-type": "app-user"}` — the client
   specifically detects this to log the user out (`Reactor.js:1022-1029`).
6. If `__admin-token` present and valid for the app → `admin? = true` (skips permission
   checks in queries/transactions).
7. Compute `features` from `versions["@instantdb/core"]` (`session.clj:93-115`):
   - `:patch-presence` if core > **v0.17.5**
   - `:skip-attrs` if core > **v0.20.4**
   - `:batch-messages` if core > **0.22.75**
8. Store on session: `:session/auth {:app app :user user :admin? admin?}`,
   `:session/creator`, `:session/features`, `:session/versions`, and (when `:skip-attrs`)
   `:session/attrs-hash (hash attrs)`.
9. Send **`init-ok`** (`session.clj:185-196`):

```clojure
(rs/send-event! store app-id sess-id
                (cond-> {:op              :init-ok
                         :session-id      sess-id
                         :client-event-id client-event-id
                         :auth            auth
                         :attrs           attrs
                         :app-status      {:status (name (app-model/get-status app-id))}}
                  (config/dev?)
                  (assoc :server-hostname @config/hostname
                         :server-port (config/get-server-port))))
```

Exact `init-ok` JSON fields:

| key | value |
|---|---|
| `"op"` | `"init-ok"` |
| `"session-id"` | server-generated squuid for this socket |
| `"client-event-id"` | echo |
| `"auth"` | `{"app": <full apps DB row, snake_case column keys, e.g. "id","title","creator_id","created_at",...>, "user": <app_users row or null>, "admin?": bool}`. The JS client ignores this field entirely (only `attrs`, `session-id`, `app-status` are read, `Reactor.js:644-659`); for wire compat it must exist, but the exact app-row keys are not client-load-bearing. Do **not** leak secrets: the row from `SELECT * FROM apps` contains no tokens, but a reimplementation should whitelist `{id, title}` + `user` + `admin?`. |
| `"attrs"` | JSON **array** of attr objects — see §6 for exact shape |
| `"app-status"` | `{"status": "active" \| "read-only" \| "disabled" \| ...}` (client defaults to `"active"` if absent) |
| `"trace-id"` | added by send-event! |
| dev only | `"server-hostname"`, `"server-port"` |

There is **no** `users` field. `processed-tx-id` is *not* part of init-ok; it comes with
each `add-query-ok`/`refresh-ok`.

On `init-ok` the client marks itself authenticated, stores attrs and session-id, flushes
queued messages, and rejoins all rooms.

### 1.3 SSE transport (for completeness)

`GET /runtime/sse?app_id=` (`runtime/routes.clj:59-63`, `session.clj:1326-1355`): on open
the server generates an `sse-token`, and enqueues an internal `:sse-init` op which sends
`{"op":"sse-init","machine-id":<uuid>,"session-id":<uuid>,"sse-token":<uuid>}` to the client
(`handle-sse-init!`, `session.clj:204-209`). Client→server messages then arrive via
`POST /runtime/sse` with body `{machine_id, session_id, sse_token, messages: [...]}`
(`sse-post`, `routes.clj:65-73`; token verified with constant-time hash compare,
`session.clj:1250-1260`). Everything downstream is identical to WS.

### 1.4 Close (`session.clj:1269-1295`)

`on-close`:

1. For every pending handler (in-flight op): run `before-cancel`, silence its exceptions,
   cancel its in-progress SQL statements, `future-cancel` its future.
2. `rs/remove-session! store app-id sess-id` (`store.clj:764-785`): retracts from the app's
   datascript conn all `instaql-query`, `subscription`, `stream`, `stream-reader` entities
   for this session (dangling `datalog-query` entities are GC'd by `tx-cleanup` +
   `clean-stale-datalog-queries-tx-data`, `store.clj:398-479`, which also invalidates their
   datalog-cache entries and cancels in-flight queries with no remaining watchers); then
   retracts the session entity; if this was the last session for the app, drops the app's
   entire conn (and its datalog cache).
3. `eph/leave-by-session-id!` (`ephemeral.clj:511-513`): leave every room the session is in
   (this triggers `refresh-presence`/`patch-presence` pushes to remaining peers).

No message is sent to the closing client.

## 2. Op handlers

Dispatch table: `handle-event` (`session.clj:974-1025`). Ops:
`:init :sse-init :add-query :remove-query :refresh :transact :error`
`:start-sync :remove-sync :refresh-sync-table :resync-table` (admin sync-table beta)
`:join-room :leave-room :set-presence :refresh-presence :client-broadcast :server-broadcast`
`:start-stream :append-stream :subscribe-stream :unsubscribe-stream` (streams beta).
Unknown op → `:error` with `status 400`, `"type":"param-malformed"`,
`"message":"Invalid op"`, `"hint":{"op": <op>}` (`session.clj:1016-1024`).

Every op except `:init`/`:sse-init`/`:error` requires prior `init` (`get-auth!`,
`session.clj:198-202`; otherwise validation error ``"`init` has not run for this session."``)
and is subject to a per-app rate-limit check (`session.clj:981-984`): if
`flags/app-rate-limited?` (a flag-configured app-id set) → typed `rate-limited` error
(status 400, message "You're making too many requests. ...", `util/exception.clj:473-478`).

Each op is executed with a timeout: default `handle-receive-timeout-ms` = **5000 ms**
(flag-overridable per app); on timeout in-progress SQL is cancelled and a typed
`operation-timed-out` error is sent (status 500 path;
`"message": "Operation timed out: handle-receive"`, `"hint": {"timeout-ms": 5000}`)
(`session.clj:1137-1207`).

### 2.1 `add-query` (`session.clj:234-270`)

Client sends `{"op":"add-query","q":<instaql query object>,"client-event-id":...}`
(optionally `"return-type":"join-rows"|"tree"`; the JS client omits it, defaulting to
join-rows).

- `q` is used **verbatim** as the store key (the keywordized-JSON Clojure value; no
  normalization — the same JSON shape must be sent in `remove-query` and is echoed back
  verbatim in responses). Duplicate detection is exact equality against the session's
  registered queries.
- If the session already has this exact `q` registered →
  `{"op":"add-query-exists","q":<q>,"client-event-id":...}` and nothing else.
- `q == null` → validation error "Query can not be null."
- Otherwise:
  1. `return-type` ← keyword of provided value or `"join-rows"`.
  2. Snapshot `processed-tx-id` and `processed-isn` for the app **before** running the
     query (`rs/get-processed-tx-id`/`get-processed-isn`, `store.clj:574-582` — the highest
     WAL tx id / ISN this server has already invalidated for; initialized from
     `tx-model/max-seen-tx-id` / max-seen ISN at conn creation, `store.clj:241-246`).
  3. Run `rq/instaql-query-reactive!` (§4) which registers the query + datalog
     subscriptions in the store, runs the (permissioned) query, and computes a result
     hash.
  4. Send **`add-query-ok`**:

```json
{ "op": "add-query-ok",
  "q": <q, verbatim echo>,
  "result": <instaql result, see below>,
  "result-meta": <object-tree meta or null; only for return-type "tree">,
  "processed-tx-id": <long>,
  "processed-isn": "<slot-hex>/<LSN>",
  "client-event-id": ... }
```

`result` format for `join-rows` (`reactive/query.clj:76-96`,
`collect-instaql-results-for-client`): a **single-element array**

```json
[ { "data": { "datalog-result": { "join-rows": [ <array of triples> ] },
              "page-info":  { "<label>": {...} },   // only if present
              "aggregate":  { "<label>": {...} } }, // only if present
    "child-nodes": [] } ]
```

where the triples of all instaql nodes are flattened and deduped into one set, wrapped in
one extra array level (`join-rows` is an array containing one array of `[e a v t]`
triples). The client reads `result[0].data["page-info"]`, `result[0].data["aggregate"]`,
and extracts triples from the whole tree (`Reactor.js:665-700`).

For `return-type: tree` the result is the instaql object tree
(`instaql-nodes->object-tree`) and `result-meta` = `instaql-nodes->object-meta` — used by
the admin SSE API, not the JS sync client.

On any exception during query execution the query is removed from the store
(`query.clj:147-149`) before the error propagates to the `:error` path (so a failed query
does not keep a stale registration).

### 2.2 `remove-query` (`session.clj:436-440`)

`{"op":"remove-query","q":<q>,"client-event-id":...}` → retracts the instaql-query entity
and its subscription entities (`rs/remove-query!`, `store.clj:628-642`; unreferenced
datalog queries get GC'd via `tx-cleanup`), then replies

```json
{ "op": "remove-query-ok", "q": <q>, "client-event-id": ... }
```

### 2.3 `refresh` (server-internal op) → `refresh-ok` (`session.clj:467-540`)

`:refresh` events are **never sent by the client**; the invalidator enqueues
`{:op :refresh :session-id id :tx-id tx-id :tx-created-at .. :isn ..}` onto the receive
queue (`invalidator.clj:246-250`). Handling:

1. Fetch all *stale* instaql queries for the session
   (`rs/get-stale-instaql-queries`, `store.clj:587-592` — those marked
   `:instaql-query/stale? true` by the invalidator).
2. Snapshot `processed-tx-id`/`processed-isn` (post-invalidation values; guaranteed ≥ the
   staleing tx because the invalidator sets them before enqueuing refresh — see §3.4).
3. Recompute each stale query in parallel (`ua/pmap recompute-instaql-query!`,
   `session.clj:442-465`). Each recomputation reruns `instaql-query-reactive!` (bumping the
   query's version, re-registering datalog subscriptions, using the datalog cache) and
   compares the new result hash against the stored one → `result-changed?`.
4. Partition into `computations` (changed) and `spam` (unchanged, dropped — "spam" is never
   sent).
5. Attrs delta: if the session supports `:skip-attrs`, compare `hash(attrs)` with
   `:session/attrs-hash`; `attrs-changed?` if different (and update stored hash). If the
   client does *not* support skip-attrs, attrs are always included.
6. If there are changed computations **or** attrs changed, send **`refresh-ok`**:

```clojure
(cond-> {:op :refresh-ok
         :processed-tx-id processed-tx-id
         :processed-isn processed-isn
         :computations (vec computations)}
  (or (not can-skip-attrs?) attrs-changed?)
  (assoc :attrs attrs))
```

Each element of `"computations"` is the full map returned by
`recompute-instaql-query!` (`session.clj:459-465`):

```json
{ "instaql-query": <q, verbatim>,
  "instaql-query-hash": <int forms-hash>,
  "instaql-result": <same format as add-query-ok result>,
  "result-meta": <or null>,
  "result-changed?": true,
  "duration-ms": <long>,
  "instaql-topic?": <bool> }
```

The client uses only `instaql-query`, `instaql-result` and top-level
`processed-tx-id`/`attrs` (`Reactor.js:733-812`), but the other keys are on the wire.

7. If nothing changed and the app has refresh throttling enabled, the handler returns a
   grouped-queue throttle so the next `:refresh` for this session is delayed
   (`session.clj:537-540`).

Note `refresh` events coalesce: consecutive `:refresh` items for a session collapse to the
latest one (`combine [:refresh :refresh]` keeps `event2`, `session.clj:1519-1524`), so one
recomputation covers many WAL transactions.

### 2.4 `transact` (`session.clj:545-584`)

Client sends `{"op":"transact","tx-steps":[...],"client-event-id":...}`.

`tx-steps` is an array of steps (spec in `db/transaction.clj:32-66`); step op names are the
strings/keywords: `add-triple`, `deep-merge-triple`, `retract-triple`, `delete-entity`,
`add-attr`, `update-attr`, `delete-attr`, `rule-params`. Triple steps are
`[op, entity-id, attr-id, value, opts?]`; `add-attr` carries a full attr object (client
sends the same casing as §6); `delete-entity` is `[op, lookup, etype?]`.
`tx/coerce!` coerces JSON values (uuids, keywords) and `tx/validate!` spec-validates;
failures raise `validation-failed` typed errors.

Flow:

1. `permissioned-tx/transact!` runs the transaction against Postgres with permission
   checks (skipped when `admin?`), producing `{tx-id, isn-promise, fallback-isn}`. `tx-id`
   is the value of the row inserted into the `transactions` table (a per-app monotonically
   increasing bigint).
2. The handler waits up to ~2.5 s (bounded so total stays under the 5 s op timeout,
   `session.clj:566-573`) for the transaction's ISN to be observed by the invalidator
   (`isn-promise` delivered from the WAL consumer, `jdbc/wal.clj:531-537`
   `tx-model/deliver-isn`); otherwise uses `fallback-isn`.
3. Sends **`transact-ok`** — once per combined redundant event plus once for this event
   (see combining, §8):

```json
{ "op": "transact-ok",
  "tx-id": <long>,
  "isn": "<slot-hex>/<LSN>",
  "client-event-id": ... }
```

The client updates the pending mutation with `tx-id` and applies any `add-attr` steps to
its local attrs (`Reactor.js:813-845`). Note: transact-ok deliberately does **not** wait
for the refresh; the client reconciles optimistic mutations when a later
`refresh-ok`/`add-query-ok` arrives with `processed-tx-id >= tx-id`.

### 2.5 `:error` — server → client error shape (`session.clj:589-616,1032-1118`)

Errors are not sent inline from the failing handler; instead the failure enqueues an
internal `:error` event on the receive queue, and `handle-error!` sends:

```json
{ "op": "error",
  "status": 400 | 500,
  "client-event-id": <echo of failing event's client-event-id, may be absent>,
  "original-event": <the entire client event that failed, minus "redundant-events",
                     plus debug-info keys when set (refresh only:
                     "processed-tx-id","processed-isn","instaql-queries")>,
  "type": "record-not-found" | "record-expired" | "record-not-unique"
        | "record-foreign-key-invalid" | "record-check-violation" | "sql-raise"
        | "permission-denied" | "permission-evaluation-failed"
        | "app-read-only" | "app-disabled" | "rate-limited"
        | "param-missing" | "param-malformed" | "validation-failed"
        | "operation-timed-out" | ... (absent for untyped 500s),
  "message": "<human string>",
  "hint": <object or absent>,
  "trace-id": ... }
```

- Status is **400** for the "expected" types listed at `session.clj:1042-1061`, **500** for
  every other typed exception and for uncaught exceptions.
- `type` is the *unqualified* keyword name (`(keyword (name type))`,
  `session.clj:1069`).
- Uncaught (non-instant) exceptions: status 500, **no `type`/`hint`**, message
  `"Yikes, something broke on our end! Sorry about that."` (`session.clj:1101-1118`).
- Well-known hints (from `util/exception.clj`):
  - `param-missing`: `{"in": [<path keys>]}`; message `Missing parameter: [...]`.
  - `param-malformed`: `{"in": [...], "original-input": <val>}`.
  - `validation-failed`: `{"data-type": <input-type>, "input": <input>, "errors":
    [{"message": ...}, ...]}`; message `"Validation failed for <type>: <joined messages>"`.
  - `record-not-found`: `{"record-type": "app"|"app-user"|..., ...}`.
  - `operation-timed-out`: `{"timeout-ms": n}`.
  - `permission-denied`: `{"input": ..., "expected": ...}`-style, plus message
    `"Permission denied: not <perm>"`.
- Errors caused by a *combined* transact are fanned out: one `:error` per redundant
  event's `client-event-id` (`session.clj:596-606`).
- If sending an error itself fails, no error-about-error is sent (loop guard,
  `session.clj:1038-1041`).
- `socket-missing`/`connection-closed` exceptions trigger `on-close` instead of an error
  message (`session.clj:1074-1080`).

Client routing (`Reactor.js:981-1067`): by `client-event-id` → mutation error; by
`original-event.op == "add-query"` (uses `original-event.q`) → query error; by
`original-event.op == "init"` → auth/status errors; else console.error.

### 2.6 Rooms/presence ops — see §5. Streams / sync-table ops (`start-sync`,
`start-stream`, etc.) are beta features; their payloads are visible in
`session.clj:272-434,756-972` and are not required for core wire compat.

## 3. Invalidation pipeline (WAL → refresh)

### 3.1 Logical replication source (`jdbc/wal.clj`)

- A Postgres **logical replication slot** with output plugin **`wal2json`** is created
  (`wal.clj:120-155`), and a replication stream started with options
  `include-lsn=true`, `format-version=2`, and
  `add-tables=public.idents,public.triples,public.attrs,public.transactions,public.rules,`
  `public.apps,public.instant_users,public.wal_logs[,_0.._7],public.webhooks`
  (`wal.clj:314-378`).
- wal2json v2 emits one JSON record per action: `begin` / `insert` / `update` / `delete`
  / `message` / `truncate` / `commit(close)`. Each change record has `table`, `action`,
  `columns` (new values: `[{"name","type","value"},...]`) and, for update/delete,
  `identity` (old/key values).
- The producer (`wal.clj:404-540`) groups records **per database transaction**: a
  transaction is only *delivered* if its first insert is into the `transactions` table
  (i.e. it is an Instant data transaction); everything else advances the LSN silently
  (cache eviction still runs on every record — this is what produces
  `app-status-changed`, attr-cache eviction, etc., `jdbc/cache_evict.clj`).
- A delivered message is `{changes, messages, lsn, nextlsn, isn, previous-isn, tx-bytes}`
  where `isn = ISN(slot-num, nextlsn)` — the strictly increasing sequence used for
  ordering across DB migrations (`isn.clj`).

### 3.2 Transform: WAL record → typed change lists (`invalidator.clj:114-153`)

`transform-wal-record` groups `changes` by table into `attr-changes` (attrs),
`ident-changes` (idents), `triple-changes` (triples), keeps `messages` + `wal_logs*` rows,
extracts `app-id`, `tx-id` (the `id` column of the `transactions` insert) and
`tx-created-at`. Records with no relevant changes or no app-id are dropped.

### 3.3 Topics (`reactive/topics.clj`)

A **topic** is a 4-tuple `[idx e a v]` describing what data a datalog query depends on:

- `idx`: a set of index keywords out of `#{:ea :eav :av :ave :vae}` (or `'_` wildcard).
- `e`, `a`, `v`: each is either `'_` (wildcard symbol), a **set** of concrete values, or —
  on the query side — a map with `{:$comparator {:op :$gt/:$gte/:$lt/:$lte/:$like/:$ilike
  :value v :data-type :number/:string/:boolean/:date}}` or `{:$not v}`.

Invalidation-side topics for a WAL record (`topics-for-changes`, `topics.clj:197-204`):

- triple insert (`topics.clj:82-90`): `[[ks #{e} #{a} #{v}]]` where `ks` = the index flags
  set on the triples row (`ea`, `eav`, `av`, `ave`, `vae` boolean columns).
- triple update (`topics.clj:92-122`): if value unchanged (or TOASTed & unchanged) → no
  topic; if same e/a → `[[ks #{e} #{a} #{v-new, v-old}]]`; else two topics.
- triple delete (`topics.clj:124-132`): from the `identity` (old) columns.
- ident insert/update (`topics.clj:146-149`): `[#{all-indexes} '_ #{attr-id} '_]`.
- attr insert/update (`topics.clj:151-167`): `[#{all-indexes} '_ #{attr-id} '_]`; when an
  *object* (non-ref) attr is restored from soft-deletion additionally `[#{:ea} '_ '_ '_]`
  (wakes every query).
- attr delete (`topics.clj:169-172`): `[#{all-indexes} '_ #{attr-id} '_]`.

Values are parsed from wal2json: `eav` values → UUID; `checked_data_type=date` → Instant;
else raw JSON value (`parse-v`, `topics.clj:72-80`).

Query-side ("datalog query") topics come from the datalog engine: coarse topics from the
patterns before execution (`d/pats->coarse-topics`) and refined topics after execution
(stored via `record-datalog-query-finish!`, see §4).

Topic matching (`store.clj:1066-1127`): a WAL topic matches a query topic iff each of the
4 positions matches: keyword=keyword; any symbol (wildcard) matches anything; set-vs-set →
non-empty intersection; set-vs-comparator-map → any element satisfies the comparator (with
NULL ordering: nil < everything, `store.clj:1055-1064`, `$like`/`$ilike` compiled to regex
mirroring Postgres semantics incl. DOTALL, `store.clj:968-1014`); set-vs-`$not` map → any
element ≠ the value. Two topic *sets* match if any pair matches; there are three
implementations (linear scan, an attr-value index, and a trie ordered idx→a→e→v) selected
by flags — all semantically identical (`store.clj:1180-1323`).

### 3.4 Invalidator worker (`invalidator.clj:193-297`)

WAL messages flow through a grouped queue keyed by **app-id** (so per-app ordering by
tx-id is preserved, cross-app parallel, max 8 workers). Consecutive records for the same
app are **combined** into one (`combine-wal-records`, `invalidator.clj:155-177`):
change lists concatenated, `tx-id`/`isn`/`nextlsn` advanced to the newest (capped at
`invalidator-batch-limit` = 500 records). Backpressure: if a flag is on and the head of an
app's queue is older than a threshold, new records for that app are dropped
(`drop-backpressure?`, `invalidator.clj:261-272`) — accepting missed refreshes over
unbounded lag.

`process-wal-record` (`invalidator.clj:213-259`) per (possibly combined) record:

1. `invalidate!` (`invalidator.clj:65-75`):
   - `topics ← topics/topics-for-changes(record)`
   - `session-ids ← rs/mark-stale-topics! store app-id tx-id isn topics record`
     (`store.clj:1444-1476`), which atomically in one datascript transaction:
     a. finds all datalog-query entities whose stored topics intersect the WAL topics
        (optionally filtered by the compiled instaql-topic program and a hard-coded
        app-specific filter, `store.clj:1424-1442` — both flag-gated optimizations that
        drop queries provably unaffected);
     b. sets `tx-meta/processed-tx-id ← max(current, tx-id)` and
        `processed-isn ← max(current, isn)` for the app;
     c. marks every instaql-query subscribed to a matched datalog query
        `:instaql-query/stale? true`;
     d. **retracts the matched datalog-query entities** (which evicts their cached
        results — the next refresh recomputes from Postgres);
     e. returns the distinct session-ids that had subscriptions on those datalog
        queries.
2. If the record contains schema changes (attr insert/delete or any ident change,
   `invalidator.clj:45-63`), the refresh set is widened to **all sockets of the app** (so
   every client learns the new attrs).
3. For each affected socket, enqueue onto the session receive queue:
   `{:op :refresh :session-id id :tx-id tx-id :tx-created-at .. :isn ..}`
   (`invalidator.clj:244-250`). (Plus `:refresh-sync-table` for matching sync-table subs.)

Ordering guarantees the Rust implementation must preserve:

- Per app, WAL records are processed in commit (LSN/ISN) order; `processed-tx-id` /
  `processed-isn` are monotone (guarded by `max`).
- `processed-tx-id` is updated **before** the `:refresh` is enqueued, and stale-marking is
  atomic with it; the `refresh` handler reads `processed-tx-id` before recomputing, so a
  `refresh-ok` always carries a `processed-tx-id` ≥ every transaction whose changes are
  reflected in its results. A query result computed *after* stale-marking may reflect even
  newer data — that is fine because the next invalidation will re-stale it.
- Because queries register a **coarse** subscription *before* running (§4), a WAL record
  arriving mid-query marks the query stale and triggers a refresh, closing the read/write
  race.
- Per session, `:refresh` events coalesce (group key `[:refresh session-id]`), so clients
  see at most one recomputation in flight and always converge to the latest state.

### 3.5 Multi-node concerns (informational)

Only one machine holds the replication slot ("singleton invalidator"); it re-broadcasts
each WAL record to all other machines over gRPC and persists them to a history table
(`invalidator.clj:342-553,783-804`). Every machine runs `process-wal-record` against its
own local store/sessions. A stateless single-node reimplementation can ignore all of this.

### 3.6 What a stateless LISTEN/NOTIFY reimplementation must replicate

Functionally required:

1. A change feed that, for every committed Instant transaction, yields
   `(app-id, tx-id, changed-triples-with-index-flags-and-old/new-values, attr/ident
   changes)`. With LISTEN/NOTIFY, the transaction writer can NOTIFY the summary itself
   (payload limits mean you may need to re-read `triples` rows by tx or store a change
   log); wal2json's old-value (`identity`) data is what enables the precise
   update/delete topics — without old values you must widen `v` to `'_` (as the byop
   path does, `topics.clj:282-307`), which is correct but refreshes more queries.
2. Per-app monotone `processed-tx-id` (the `transactions.id` value), returned in
   `add-query-ok` and `refresh-ok`. (`processed-isn` exists for DB-failover ordering;
   a stateless server can synthesize it, e.g. `"0/<hex tx-id>"` — the client stores but
   does not interpret it.)
3. Topic extraction per §3.3 and matching per §3.3 against the topics of each
   *currently registered* query; alternatively — the simple stateless strategy — skip
   topic bookkeeping and re-run **all** of a session's queries on any matching app
   change, relying on the result-hash comparison to suppress unchanged `refresh-ok`s.
   Topics are purely an optimization; correctness only requires "refresh at least the
   affected queries, and send only changed results".
4. Coalescing: collapse pending refreshes per session; recompute once.
5. The attrs-changed fast path: on any attr/ident change, refresh **all** sessions of the
   app and include `attrs` in `refresh-ok` (or always include attrs for clients without
   `:skip-attrs`).
6. `app-status-changed` pushes on `apps.status` updates (§7).

## 4. Datalog query caching model (rs store)

Structure (per app, one datascript conn + one Caffeine async cache,
`store.clj:56-259`):

- `instaql-query` entity: `{session-id, query, forms-hash, stale?, version, hash
  (result-hash), return-type, topic (compiled instaql-topic)}` — unique on
  `[session-id, query]`.
- `datalog-query` entity: `{app-id, query (datalog patterns), topics, watchers,
  stmt-tracker, child-vfutures}` — unique on `[app-id, query]`, **shared across sessions
  and instaql queries**.
- `subscription` entity: `{app-id, session-id, instaql-query → ref, datalog-query → ref,
  v}` — the edge used both for invalidation fan-out and GC.
- Cached datalog *results* live in a weight-bounded (default 500 MB × multiplier), TTL
  (1 h) async cache keyed by datalog-query entity id (`store.clj:221-235`); evicting the
  datascript entity invalidates the cache entry and cancels the query if in flight.

Execution flow (`reactive/query.clj:108-149` + `store.clj:594-949`):

1. `bump-instaql-version!`: create-or-bump the instaql-query entity (version++,
   `stale? = false`).
2. Run the instaql query with a wrapped `datalog-query-fn` that, per datalog subquery:
   a. `record-datalog-query-start!` — upserts the shared datalog-query entity with
      **coarse** topics (from patterns alone) and creates a `subscription` row with the
      current version. This happens *before* the SQL runs → no missed invalidation.
   b. `swap-datalog-cache!` — one-flight result sharing: get-or-compute the
      CompletableFuture in the cache; concurrent identical queries (across sessions)
      share one SQL execution.
   c. `record-datalog-query-finish!` — replace topics with the **refined** topics
      computed from the actual result.
3. `add-instaql-query!` — retract subscriptions from older versions of this instaql query
   (removing datalog deps no longer used) and store the result hash; `result-changed?` =
   hash differs from previous (or both nil).
4. Result hash includes the attrs: `hash {:instaql-result r :attrs attrs}`
   (`query.clj:136-137`) — so an attr change flips `result-changed?` even for identical
   rows.

Invalidation deletes matched datalog-query entities outright (cache eviction); a refresh
then recomputes only the instaql queries marked stale, re-priming shared cache entries
once per unique datalog subquery.

**Stateless takeaway**: all of this is server-local performance machinery. A stateless
server must recompute stale instaql queries from Postgres on refresh; it must keep, per
(session, q): `return-type` and the last **result hash** (to suppress unchanged
computations and duplicate `add-query` registrations), and per app the `processed-tx-id`.
The datalog-level cache/subscription sharing is optional. The one semantic it must not
lose: the result-changed comparison keys on (result, attrs).

## 5. Presence / rooms (`reactive/ephemeral.clj`, handlers in `session.clj:638-754`)

Room state is a distributed map (Hazelcast `IMap "rooms-v2"`) keyed by
`{app-id, room-id}` with value:

```clojure
{<sess-id> {:peer-id     <session-id>
            :instance-id <machine instance id string>
            :user        {:id <user-id>} | nil
            :data        <arbitrary presence json>}}
```

(`ephemeral.clj:280-287`, merge logic `util/hazelcast.clj:123-172`). `room-id` is an
arbitrary **string** (validated `string?`, `session.clj:638-641`). Per-app+room, updates
are applied via per-key queues (`eph-update-queue`) so they're serialized per room.

### 5.1 `join-room` (`session.clj:643-653`)

In: `{"op":"join-room","room-id":"...","client-event-id":...,"data":<initial presence or
absent>}` (the client also sends `roomType`, ignored by the server). Requires app reads
allowed (`app-model/assert-read-allowed!` → typed `app-disabled` error otherwise).
Registers the session locally and merges
`{peer-id, instance-id, user, data: (or existing data {})}` into the room map. Reply:

```json
{ "op": "join-room-ok", "room-id": "...", "client-event-id": ... }
```

(There is no server-sent `join-room-error` op in the current server; failures use the
generic `error` op. The client's `join-room-error` case is legacy.)

### 5.2 `set-presence` (`session.clj:671-680`) — **full replace**

In: `{"op":"set-presence","room-id":"...","data":<full presence value>,...}`. Must be in
the room (else validation error "You have not entered this room yet."). Replaces the
session's `:data` wholesale (`SetPresenceMergeV1`, `hazelcast.clj:157-168`). Reply:
`{"op":"set-presence-ok","room-id":...,"client-event-id":...}`. There is no
patch-*upload* op — patching exists only server→client.

### 5.3 Presence fan-out: `refresh-presence` / `patch-presence`

Any change to a room's map entry (join/leave/set-presence, from any machine) fires the
entry listener → `process-event` (`ephemeral.clj:298-317`): for every *local* session in
that room it enqueues an internal event

```clojure
{:op :refresh-presence :app-id .. :room-id ..
 :data room-data                      ;; the full new room map
 :edits (when-not just-joined? edits) ;; editscript diff old→new, nil for fresh joiners
 :session-id sess-id}
```

`edits` = `editscript/get-edits (editscript/diff last-data room-data {:algo :a-star
:str-diff :none})`. `handle-refresh-presence!` (`session.clj:682-700`) then sends, per
session:

- If `edits` present but empty: nothing (nop).
- If `edits` present and the session supports `:patch-presence`:

```json
{ "op": "patch-presence", "room-id": "...", "edits": [ [ <path>, <op>, <value?> ], ... ] }
```

  Edit format (editscript vectors): `path` is an array of keys into the room map (session
  ids serialize as strings; map keys such as `data` as strings; array indices as
  numbers); `op` is `"+"` (add), `"r"` (replace), or `"-"` (delete, no value element).
  E.g. `[["<sess-id>","data","cursor"], "r", {"x":10,"y":20}]`. The client applies exactly
  these three ops (`Reactor.js:2672-2696`) and ignores edits touching its own session id.

- Else (no edits — fresh join — or old client):

```json
{ "op": "refresh-presence", "room-id": "...",
  "data": { "<sess-id>": { "peer-id": "...", "instance-id": "...",
                            "user": {"id": "..."} , "data": {...} }, ... } }
```

  The client keeps `v.data` per peer and drops its own entry (`Reactor.js:2698-2710`).

Coalescing: consecutive `:refresh-presence` internal events for the same
(session, room) concatenate their `edits` (`combine`, `session.clj:1526-1527`); consecutive
`:set-presence` uploads collapse to the latest (`session.clj:1529-1530`).

### 5.4 Broadcast (`session.clj:702-754`)

In: `{"op":"client-broadcast","room-id":"...","topic":"...","data":<json>,
"client-event-id":...}` (client also sends `roomType`; ignored). Must be in the room.
Builds:

```clojure
base-msg {:room-id room-id
          :topic topic
          :data {:peer-id sess-id
                 :user (when current-user {:id (:id current-user)})
                 :data data}}
```

- To every **other local** room member: enqueue internal `:server-broadcast`; to remote
  members: publish `{app-id, session-ids, base-msg}` on the Hazelcast topic, whose
  receiving machines enqueue the same internal `:server-broadcast` per local session
  (`ephemeral.clj:351-364,390-394`).
- Echo to sender:

```json
{ "op": "client-broadcast-ok", "room-id": "...", "topic": "...",
  "data": { "peer-id": "<sender sess-id>", "user": {"id":"..."}|null, "data": <payload> },
  "client-event-id": ... }
```

`handle-server-broadcast!` (`session.clj:733-754`) delivers to each recipient **iff still
in the room**:

```json
{ "op": "server-broadcast", "room-id": "...", "topic": "...",
  "data": { "peer-id": "<sender>", "user": ..., "data": <payload> } }
```

Consecutive queued server-broadcasts for one (session, room) combine into a batch; if the
client supports `:batch-messages` they are sent as a JSON **array** of up to 500 such
message objects in a single WS frame, otherwise as individual frames
(`session.clj:739-754`; note the feature lookup uses key `:features` instead of
`:session/features` — a bug that makes the array path effectively dead; individual sends
are the observed behavior).

### 5.5 `leave-room` / disconnect

`{"op":"leave-room","room-id":...}` → removes the session from local maps + the
distributed map → `{"op":"leave-room-ok","room-id":...,"client-event-id":...}`. On socket
close, `eph/leave-by-session-id!` leaves every joined room (peers get presence
refresh/patch). A minute-interval janitor removes sessions whose machine is gone
(`clean-orphan-sessions`, `ephemeral.clj:428-451`).

**Stateless reimplementation**: single-node, replace Hazelcast with an in-process map of
`{(app-id, room-id) → {sess-id → {peer-id, user, data}}}` (an `instance-id` field is on
the wire inside `refresh-presence` data but unused by the client), serialized per room,
diffed with an editscript-compatible differ for `patch-presence` (or always send
`refresh-presence` — protocol-legal for all clients, since patch is gated on the *server*
choosing to send edits).

## 6. Attrs delivery and serialization

When sent: (a) `init-ok.attrs` — always; (b) `refresh-ok.attrs` — when the client lacks
`:skip-attrs` (core ≤ 0.20.4), or when `hash(attrs)` changed since last send; never in
`add-query-ok`. There is no separate attrs op. New-attr propagation relies on schema
changes refreshing *all* app sessions (§3.4 step 2). The client also appends attrs locally
from its own `add-attr` tx-steps on `transact-ok`.

An attr serializes as (from `row->attr`, `db/model/attr.clj:844-889`, via cheshire —
kebab-case and `?` preserved):

```json
{ "id": "<uuid>",
  "value-type": "blob" | "ref",
  "cardinality": "one" | "many",
  "forward-identity": ["<ident-uuid>", "<etype>", "<label>"],
  "unique?": true|false,
  "index?": true|false,
  "required?": true|false,
  "inferred-types": ["string", ...] | null,
  "catalog": "user" | "system",
  // optional keys, present only when set:
  "on-delete": "cascade",
  "on-delete-reverse": "cascade",
  "reverse-identity": ["<ident-uuid>", "<etype>", "<label>"],
  "checked-data-type": "string"|"number"|"boolean"|"date",
  "checking-data-type?": true,
  "indexing?": true,
  "setting-unique?": true,
  "deletion-marked-at": "<timestamp>",
  "metadata": { ... } }
```

`"attrs"` is a JSON array of these (the `Attrs` wrapper type serializes as a seq). The
client indexes them by `id` verbatim (`Reactor.js:1076-1082`) and its schema/tx layers
read exactly these kebab-case keys (`forward-identity`, `reverse-identity`,
`value-type`, `cardinality`, `unique?`, `index?`).

Attrs equality/hash for `:skip-attrs` uses Clojure `hash` on the unwrapped attr list
(`session.clj:184,504`); any stable hash works as long as it changes when any attr
changes.

## 7. Miscellany worth matching

- **`app-status-changed`** (`jdbc/cache_evict.clj:74-83`, `sunset.clj:26-35`): pushed
  best-effort to every session of an app when `apps.status` changes (via WAL cache-evict
  path) or when a global sunset stage flips:

  ```json
  { "op": "app-status-changed", "status": "active" | "read-only" | "disabled" | ... }
  ```

  Client behavior (`Reactor.js:899-920`): `disabled` → error out all queries;
  leaving `disabled` → restart the socket.

- **Keepalive**: WS protocol-level ping every 5 s from the server; server closes after
  15 s of silence (§1.1). The client does not send app-level pings; it *does* reconnect on
  close. SSE has a retry-interval hint (`session.clj:1376-1378`, default 500 ms).

- **Timeouts**: per-op processing timeout 5 s (flag-overridable per app) → typed
  `operation-timed-out` error; transact additionally bounds its ISN wait to ≤ 2.5 s.

- **Rate limiting**: per-app flag-driven kill switch checked before every op except
  init/error (`session.clj:981-984`) → `rate-limited` error, status 400. Room updates go
  through a bucket4j limiter infra (`rate-limit/initialize`), and app reads can be blocked
  entirely (`app-model/assert-read-allowed!` on join-room → `app-disabled`).

- **Message size limits**: no explicit WS frame limit in the server; the practical bound
  is cheshire's default max JSON string length (20,000,000 chars) on parse
  (`util/json.clj:68-70` raises it only for internal WAL parsing). The sync-table path
  chunks outgoing txes at 100/frame (`session.clj:390-404`) and server-broadcast batches
  at 500/array; core protocol messages are unchunked.

- **Grouped receive queue ordering** (`grouped_queue.clj`, keys at
  `session.clj:1463-1510`): items with the same group key run **sequentially in FIFO
  order**; different keys run in parallel. Keys: `[:transact session-id]`,
  `[:query session-id q]` (add/remove-query share a key → add then remove can't
  reorder), `[:refresh session-id]`, `[:room session-id room-id]` (join/leave/presence/
  broadcast serialized per room), `[:refresh-presence session-id room-id]`,
  `[:error session-id]`, `[:init session-id]`; unknown ops get a random key (fully
  parallel). Combining (`session.clj:1512-1553`): refresh+refresh → keep latest;
  refresh-presence → concat edits; set-presence → keep latest; server-broadcast →
  batch payloads; transact+transact → merged only when both are pure cardinality-one
  `add-triple` step lists over identical (e, a) pairs (flag-gated;
  `matching-steps?`, `session.clj:1404-1450`), replying `transact-ok` once per merged
  client-event-id. **Note**: a query's SQL work runs on a future with only the *wait*
  bounded per group; practically, per-key serialization is the contract to honor.

- **`add-query-exists`**: don't forget this op (§2.1) — the client resolves
  `queryOnce` promises on it (`Reactor.js:661-663`).

- **Unknown server→client ops** are logged and ignored by the client, so additive server
  messages are safe.

## 8. Minimal wire-compatible server checklist

State per session: `auth {app, user, admin?}`, `features`, `attrs-hash`, registered
queries `{q → {return-type, last-result-hash}}`, joined rooms. State per app:
`processed-tx-id` (+ fake `processed-isn`), room maps. Handle ops per §2/§5; on data
change: compute topics (or over-approximate), pick affected sessions, coalesce, recompute
changed queries, send `refresh-ok` with `computations` + `processed-tx-id` (+ `attrs` when
needed); on schema change: refresh everyone with `attrs`. Reply shapes and key casing
exactly as quoted above.
